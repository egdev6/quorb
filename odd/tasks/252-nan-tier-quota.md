## Mecanismo (verificado en el código)

- Dos rutas en `providers/nan.rs::fetch`: A) sesión de NaN Cloud (`nan_cloud::fetch`, cookie) y B) API key (`/v1/models` + `/v1/usage`, Bearer). La ruta A devuelve temprano si hay `secrets::NAN_SESSION`.
- El denominador era la cuota *publicada*: `known_quotas()` (`nan.rs:32-50`) y, si `/v1/models` expone un campo con "quota", ese (`nan.rs:137`, `quotas_from_models`). Ninguna de las dos es la asignación de la cuenta.
- La ruta A leía solo `cap` (`nan_cloud.rs:187`); la ruta B dividía con `used / q.tokens` (`nan.rs:489`). Ninguna de las dos tenía la asignación de la cuenta.
- **Payload real** de `GET https://cloud-api.nan.builders/api/usage/quota`, consultado con la API key de la cuenta (sin cookies ni cabeceras de sesión): en la raíz, `periodStart` y `models`; por modelo, `model`, `tokensUsed`, `cap`, `remaining`, `periodEnd`, `extraTokens` y `extraUsable`. **No existe `fullCap`.** `cap` es la asignación de la cuenta para el periodo en curso: 1.000M para `deepseek-v4-flash` y 500M para `glm5.3-flash`, los mismos números que el panel muestra como "Allowance per billing period".
- `/v1/models` no expone cuota alguna (sus objetos solo traen `created`, `id`, `object` y `owned_by`): por eso la tabla local era la única fuente posible del denominador en la ruta B.
- `/v1/usage` mide el consumo **de la API key** (917,78M y 496,63M) y el payload de Cloud mide el consumo **de la cuenta** (955,58M y 496,63M): la diferencia (37,8M) es uso que no pasa por esta key. Con el arreglo, cuota, uso y fechas salen del mismo payload de cuenta.
- `windowHours` decide el inicio del periodo del medidor (con ventana → `periodEnd` − 1 mes; sin ventana → `periodStart`, `nan_cloud.rs:198`): se conservó byte a byte porque no pertenece al arreglo (S4). El payload real no trae esos campos; el fixture antiguo sí.
- La tabla local no sigue la cuota que devuelve el proveedor: publica 3.000M y 2.000M y la cuenta tiene 1.000M y 500M. Los ids sí coinciden (`glm5.3-flash`).
- Referencia de la misma API con la misma credencial: el paquete `gentle-pi` divide por `fullCap ?? cap` (`lib/shell-usage.ts:360-366`) y su proveedor de NaN es solo API key (`lib/nan-provider.ts:198-200`), con `Authorization: Bearer` contra el mismo endpoint (`extensions/gentle-shell.ts:1994-2000`). **Se consultó como pista, no como verdad**: el endpoint y la credencial son los correctos, pero el campo `fullCap` no existe en la API real.

El denominador es `cap`, y el primer periodo prorateado llega prorateado: no hace falta ningún caso especial ni una tolerancia a un campo que la API no expone.

El seam de `e399972` tampoco cambia el comportamiento: misma URL, mismas cabeceras y mismo texto de error, con el envío y el parseo centralizados en `send_json` y el transporte cubierto por dos tests.
